# Patch the loyalty object after each confirmed stamp

Update a customer's pass with an authenticated `PATCH` on the `loyaltyObject` resource at `walletobjects.googleapis.com`, using the Stampy service account and the scope `https://www.googleapis.com/auth/wallet_object.issuer` ([PATCH reference](https://developers.google.com/wallet/retail/loyalty-cards/rest/v1/loyaltyobject/patch), [auth guide](https://developers.google.com/wallet/retail/loyalty-cards/getting-started/auth/rest)). The body is a partial `LoyaltyObject` carrying `loyaltyPoints.balance.int` plus the full `textModulesData` array, so the `user_progress` text and the balance never disagree. The docs do not state whether PATCH merges or replaces arrays, so sending all three text modules (`reward_info`, `stamps_info`, `user_progress`) every time is the safe choice. Updates are silent unless `notifyPreference` is sent on that request, and push is capped at about 3 per pass per 24 hours, so notify only on the reward-reached event. Stampy's `wallet.service.ts` has no REST client today: it only builds "save to wallet" JWT links containing both class and object. Updating therefore needs a new, best-effort call after the stamp transaction commits, because the PostgreSQL row (`stamps_count`) stays the source of truth and the Wallet pass is a derived view. Several behaviors are not in the fetched docs (pre-save PATCH, latency, error codes, quotas, merge semantics), and the list of UNVERIFIED items below must be tested against a demo issuer before relying on them. Source caveat: all pages were read through a summarizing fetch tool on 2026-10-30, so wording is paraphrased and critical points should be re-read on the pages themselves.

## Auth, endpoint and PATCH versus PUT

The endpoint is `PATCH https://walletobjects.googleapis.com/walletobjects/v1/loyaltyObject/{resourceId}`, where `resourceId` is `issuerId.identifier` (alphanumerics, `.`, `_`, `-`). Request and response bodies are a `LoyaltyObject`, and the scope is `wallet_object.issuer` ([PATCH reference](https://developers.google.com/wallet/retail/loyalty-cards/rest/v1/loyaltyobject/patch)). In Stampy that resource id is exactly `card.walletObjectId`, which `buildObjectId(cardId)` already formats as `WALLET_ISSUER_ID.cardId`. PUT (`update`) lives at the same URL with the same scope and returns the updated object, but the page does not say whether it replaces the whole object ([update reference](https://developers.google.com/wallet/retail/loyalty-cards/rest/v1/loyaltyobject/update)). The PATCH page says only that it "supports patch semantics". Because PUT could drop fields not resent (UNVERIFIED), PATCH is the right verb for a one-field change.

Auth setup is the same as for the existing JWT flow: enable the Google Wallet API, create a service account with a JSON key, and invite the service account email in the Pay & Wallet console with the Developer access level. The key identifies Stampy as the pass issuer and must stay server-side ([auth guide](https://developers.google.com/wallet/retail/loyalty-cards/getting-started/auth/rest)). The service account already loaded by `loadServiceAccount` can be reused. The pages fetched do not show the HTTP header form or token lifetime; the standard OAuth2 pattern (a bearer access token obtained via `google-auth-library` with the scope) is an inference, not a documented fact here (UNVERIFIED).

## Which fields to send, and what a class edit does

`loyaltyPoints.balance` accepts exactly one of `string`, `int`, `double` or `money`, so the `{ int: card.stampsCount }` already built in `buildLoyaltyObject` is valid. Recommended display maximums are 9 characters for the label and 7 for the balance ([LoyaltyObject reference](https://developers.google.com/wallet/retail/loyalty-cards/rest/v1/loyaltyobject)). The same page lists `textModulesData` (up to 10 shown from the object and 10 from the class), `messages` (max 10), `state` and `validTimeInterval`. An object whose `state` is inactive moves to the "Expired passes" section, which is the mechanism to retire a card after a reward is redeemed or a promotion ends. `id` and `classId` are marked required, and the docs fetched say nothing about whether they can be changed; treat them as immutable and never include them as edits (UNVERIFIED as a documented rule).

For the PATCH body, the recommended payload is `loyaltyPoints` (label plus new balance) and the whole `textModulesData` array, built by the same function that builds the save link so the "n/m timbri raccolti" string comes from one place. Per the project rule, the n/m split itself must still come from `splitStamps` in `utils/stamps.ts`; a full card (`stamps_count = stampsRequired`) is reward available and not an error, so the pass should simply show the full count.

Class edits are possible through insert, patch and update. The class page states that `reviewStatus` can be set to `draft` or `underReview` through them, cannot go back to `draft`, and that an already approved class should keep `underReview` when updated ([LoyaltyClass reference](https://developers.google.com/wallet/retail/loyalty-cards/rest/v1/loyaltyclass)). The code builds the class with `reviewStatus: "UNDER_REVIEW"` (commented as `APPROVED` in production); the docs say the platform sets approved, so production code should keep sending `underReview` on class updates. Which class fields propagate to existing objects, and whether editing an approved class triggers a re-review that blocks objects, are not documented (UNVERIFIED). Branding changes (logo, colors) are therefore a separate, lower-priority flow from stamp updates.

## Before the customer adds the pass: object must exist first

The only documented creation path in the notes is the save JWT: "When a user saves the pass, the pass class and object defined in the JWT are created" ([JWT use case](https://developers.google.com/wallet/retail/loyalty-cards/use-cases/jwt)). Stampy's current JWT embeds the full class and object. If the object exists in the issuer only after the first save, a PATCH sent before the save would most likely return not found (inference, UNVERIFIED). Two designs follow. Option A keeps the current flow and treats "not found" as "not saved yet": skip silently, and rely on the JWT built from the current `stamps_count` when the customer eventually taps the link, because `buildLoyaltyObject` reads the live card. Option B first inserts the class and object via REST, so PATCH always works and the save link can reference the object by id; whether a save link may reference an already existing object, and what the platform does when a full JWT carries an object that exists, are not documented (UNVERIFIED). Option A needs no extra code path and fits the MVP rule against speculative abstractions, with the one risk that a link generated earlier carries stale stamps. Regenerating the save URL on each `visit`, as `visit` does via `createSaveUrl`, removes most of that risk.

Detecting that the pass was added relies on the class `callbackOptions.url`: Google calls it on every save and delete by a user, with class id, object id, event type `save` or `del`, expiration time and nonce. The signature must be verified against Google's public keys, delivery is best-effort with retries (duplicates possible), and the URL must be HTTPS with a robots.txt that allows Googlebot ([callbacks guide](https://developers.google.com/wallet/retail/loyalty-cards/use-cases/use-callbacks-for-saves-and-deletions), [CallbackOptions](https://developers.google.com/pay-wallet/products/wallet/reference/rest/v1/CallbackOptions); both read only via search summaries). The object has a platform-set `hasUsers` boolean that a GET could read, but the docs do not present it as a supported status check. Classes and objects cannot be deleted through the API; users can only remove them from their own wallet ([FAQ](https://developers.google.com/wallet/docs/faq), search summary only). A callback handler would be a new public, unauthenticated endpoint and is not needed for the best-effort design; it is only worth building if Stampy wants to store "pass added" state, and it would need its own rate limit, signature check and idempotent handling.

## Notifications are opt-in per request and capped

A PATCH or PUT changes the pass silently unless `notifyPreference` is sent, and the setting is ephemeral, so it must be set on each request ([push notifications guide](https://developers.google.com/wallet/retail/loyalty-cards/use-cases/trigger-push-notifications)). Only an allowlist triggers a notification: on the object `loyaltyPoints.balance` and `secondaryLoyaltyPoints.balance`, on the class `rewardsTier`, `secondaryRewardsTier` and `programName`. The user must have Wallet notifications enabled. Three sources name the value differently: the guide says `notifyOnUpdate`, the object reference describes the enum `NotificationSettingsForUpdates` with `NOTIFY`, `DO_NOT_NOTIFY` and unspecified, and the field notes list `NOTIFY_ON_UPDATE` ([LoyaltyObject reference](https://developers.google.com/wallet/retail/loyalty-cards/rest/v1/loyaltyobject)). The accepted literal is UNVERIFIED and must be tested. An alternative is `addMessage` (POST `.../loyaltyObject/{resourceId}/addMessage`) with `messageType` `TEXT_AND_NOTIFY`, which writes a message on the back of the pass and pushes ([addMessage reference](https://developers.google.com/wallet/retail/loyalty-cards/rest/v1/loyaltyobject/addmessage)).

The limit is up to **3 push-triggering messages or updates per 24 hours**, per pass according to the summary; beyond that the API reports `QuotaExceededException` and later updates can be sent as plain `TEXT`. Every confirmed stamp changes the balance, so notifying on each would exhaust the cap quickly. The recommendation is no notification on ordinary stamps (the pass refreshes silently) and a single notification when `stamps_count` reaches `stampsRequired`. The push guide gives no delivery latency, and no page found documents how fast a silent update appears on the device (UNVERIFIED). The UI should therefore not promise instant refresh; the staff web app confirmation is the authoritative feedback.

## Recommended implementation for Stampy and what to test

The recommended design keeps the database correct and treats Wallet as a best-effort projection. First, the stamp request confirmation commits in PostgreSQL exactly as today, with no change to its transaction. Second, after commit, a new method on `GoogleWalletService` (for example `updateCardPass(card, promotion)`) builds the object with the existing `buildLoyaltyObject`, picks the fields to send (`loyaltyPoints`, `textModulesData`), and issues the PATCH with a short timeout. Third, any failure is logged without personal data (no emails, codes or IPs; the card id and HTTP status are enough) and swallowed, so a Google outage or a not-yet-saved pass never fails the staff confirmation. Fourth, because the PATCH carries absolute values (the new balance, not an increment), it is naturally repeatable, so a retry or a later "resync from DB" job converges to the right state; a bounded retry on transient errors is enough for the MVP. Do not use `new Date()` or any client-supplied value in the payload: the numbers come from the committed card row. Per the project rules, the change also requires updating `CODEBASE.md`, adding a test script in `scripts/` that mocks the HTTP client, and moving or adding the relevant `BACKLOG.md` items, and any quota or error-code claim must be marked UNVERIFIED until checked against official docs.

## Conclusion

The decisive finding is a gap, not a feature: the docs describe how to send a PATCH and how to notify, but say nothing about the behavior that matters most to Stampy, which is what happens to an update when the customer has not yet saved the pass. That is why the design makes Wallet disposable: the database holds the stamps, the save link is regenerated from live data, and a failed or skipped PATCH costs only a stale pass until the next update or visit.

The practical next step is a one-day spike on a demo issuer that answers items 1, 4, 5 and 6 of the table; those four results decide the array strategy, the not-saved handling, the creation path and the notification literal, and everything else in the recommended flow stands regardless of the outcome.
